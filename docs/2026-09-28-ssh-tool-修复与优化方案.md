## 修复清单

### P0：把 shell 语法组合变成安全边界

**证据位置**：`src/scheduler/command-classifier.ts` 的 `classifyCommand()`、`commandCandidates()`、`splitTopLevelCommands()`。

现在分类器依赖很小的字符扫描。单段命令先按开头命中规则；多段命令会扫描顶层分隔符，却没有递归识别 `$()`、反引号、`>` / `>>`、括号、变量展开和包装 shell，所以 `echo` 前缀能遮蔽写文件或执行嵌套命令的语义。`src/scheduler/command-classifier.ts` 的 `isNeutralShellSegment()` 还把 `export`、`cd` 和简单赋值开头的片段视为中性，即使它们内部含命令替换；本地纯函数检查再次确认三种中性前缀都可掩盖嵌套执行。

**建议改法**：

1. 不把有限规则匹配器描述成 shell 解析器。先识别是否存在 shell 复合结构；仅允许 parser 明确覆盖且完整遍历的语法参与自动低风险分类。
2. 对重定向、命令替换、反引号、子 shell、复合赋值、shell `-c` 包装等当前未完整处理的语法，返回 `custom/large/risky=true/mutates=true`，要求 `force`。`cd`、`export`、赋值和其他“中性片段”也必须先做同样的内部扫描。
3. 对已支持的顶层段逐段分类，聚合全局最高风险：`risky` 与 `mutates` 取 OR，`cost` 取最大级别，`blocking` 取 OR。未知段不得被已知只读段覆盖。
4. 分类失败时保守拒绝自动低风险；提供明确原因，让用户可通过显式确认继续。
5. 保持 blacklist/whitelist 安全策略独立生效，不用 scheduler 的 `force` 取代命令白名单校验。

**必须有的回归用例**：`echo ok > file`、`echo $(rm …)`、反引号、`export X=$(...)`、`X=$(...); echo done`、`cd $(...) && echo done`、`cat file > out`、`pwd && systemctl restart ...`、只读前缀加未知脚本。引号内的 `; | >` 不应误判成外层语法；安全的 `echo "a;b"` 和 `echo '$(rm)'` 不应被当作执行了内层语法。对危险样例只断言分类，不实际执行。

**验收**：这些组合不再得到 `inspect/tiny/risky=false/mutates=false`；调度器弹出确认并拿到相应锁；普通只读命令与引号内符号仍保持低风险。

### P0（npm 发布阻断）：发布包漏了 `dist/remote-dialect/`

**证据位置**：`package.json` 的 `files` 清单包含 `dist/*.js`、`dist/cli/`、`dist/scheduler/`、`dist/coordinator/`，没有 `dist/remote-dialect/`。`dist/gateway.js`、`dist/daemon.js` 和 `dist/file-transfer.js` 均静态导入 `./remote-dialect/index.js`；`dist/file-transfer.js` 还导入 `./remote-dialect/powershell.js`。当前本地 `dist/remote-dialect/` 存在，但 `npm pack --dry-run --ignore-scripts --json` 返回的 212 个打包文件里，`dist/remote-dialect/index.js`、`posix.js`、`powershell.js`、`cmd.js` 全部缺席。

**影响范围**：从源码仓库直接启动 Trae MCP 时文件齐全，运行不受这一项影响。用当前 `files` 清单制作 npm 包后，主入口与 CLI/daemon 所需的方言模块不在包内，安装者无法正常加载入口。这是发布包完整性问题，不应以仓库内 `npm test` 绿灯放行 npm 发布。

**建议改法**：

1. 在 `package.json#files` 明确加入 `dist/remote-dialect/`，保留该目录的 `.js`、`.d.ts` 和必要 sourcemap。
2. CI 在隔离临时目录里执行 `npm pack --dry-run --ignore-scripts --json`，校验 package `main`、全部 bin 入口和所有编译后相对 JS import 的目标都在文件列表中。
3. 再把真实 tarball 安装到隔离临时项目，运行 `import('ssh-tool')` 与 `ssh-exec --help` 的最小装包检查。测试进程必须使用隔离的 `SSH_TOOL_DATA_DIR`、`SSH_TOOL_CACHE_DIR`。
4. 发布前对照 `npm pack` 的内容清单与当前编译输出，不允许靠本地仓库残留文件让装包检查误通过。

**验收**：包内存在整个 `dist/remote-dialect/` 运行时模块树；在没有源码仓库的临时环境中，主入口和 CLI 帮助命令均能加载；CI 在漏文件时明确失败。

### P1：完成传输的 deadline、原子写入与 backup 错误处理

**证据位置**：`src/file-transfer.ts` 中 `openSftp()`、`uploadFile()`、`uploadFileDirect()`、`downloadFile()`、`checkOverwrite()`；调用方在 `src/cli/ssh-exec.ts`、`src/daemon.ts` 和 `src/mcp-server.ts`。

已完成：SFTP channel 打开纳入用户传入的 timeout；MCP/CLI 暴露传输 timeout；下载本地目标改用临时文件。仍需修：

1. FileTransferOptions 的注释写有默认 2 分钟、FolderTransferOptions 写有默认 5 分钟，但 timeout 不传时当前没有 timer。实现真实默认值：单文件 120 秒、目录操作 300 秒，或者更改接口说明并明确无限制运行不被支持。
2. CLI IPC transfer 请求目前固定等待 300 秒。IPC 等待期限必须至少覆盖实际传输 deadline 加清理余量；IPC 超时后应取消 daemon 内任务，或返回可查询的 transfer task id，不能让调用方以为失败而远端继续写入。
3. 小文件和大文件上传现在会在 SFTP 支持 rename 时先写同目录唯一临时文件，完成后再替换目标；仍需在真实 POSIX/Windows SFTP 服务端验证目标已存在时的替换/回滚语义，并为不支持 rename 的服务器定义明确降级策略。
4. 下载临时文件替换要覆盖 macOS/Linux 及 Windows 本地目标已存在的情况。Windows `renameSync` 覆盖现有文件语义不同；需显式 backup/replace/rollback 并测试。
5. `remotePathExists()` 把所有探测错误折叠为“不存在”；`remoteIsDir()`、`remoteIsSymlink()` 也把异常折叠为 false。改成 exists / missing / error 三态，区分“不是目录/软链”和“未能判定”。网络/权限错误必须中止，不能按目标不存在或非软链继续写。
6. `overwrite: backup` 的远端 `remoteExec` 结果必须检查 exit code；备份失败就停。当前本地 backup 也会在移动失败时继续覆盖；改为立即报错。不能静默删除已存在的 `.bak`，需要版本化备份名或明确失败。
7. timeout 到达后取消/销毁所有流和 SFTP channel，删除本次 staging 文件，保留原目标。目录递归传输要共享一个总 deadline，不能每个文件重置整个预算。

**验收**：在开 SFTP 不回调、stat 永不返回、路径类型探测失败、下载中途断开、上传中途断开、校验失败、backup move 非零、目标已存在、目标路径含空格和 Windows 路径等故障注入下，超时有界、旧目标保持完整、备份失败不覆盖、临时文件可识别并清理。

### P1：统一远端方言的探测时序与工作目录传递

**证据位置**：`src/gateway.ts:68-87`、`src/remote-dialect/index.ts:29-35`、`src/daemon.ts:180-192,258-297,1127-1147`、`src/mcp-server.ts:1048-1053,1341-1350`。

发现的是几处相互独立的调用链问题：

1. `connectByChain()` 在连接成功后启动 `probeRemoteDialect(session).catch(...)`，随即返回。`getDialect()` 在缓存尚未填入时回退 POSIX。紧接连接的第一条 Windows 命令可能先用 POSIX wrapper 发出；缓存稍后更新也无法改变已经发出的命令。
2. 调度前台任务的 `execScheduledStream()` 把 `cwd` 预先写成 `cd ${shellQuote(cwd)} && command`，然后才调用方言 `buildExec()`；后台任务也采用同样的 POSIX 风格前缀，再交给 `buildBackground()`。PowerShell 与 CMD 方言本来都提供 `buildExec(command, { cwd })` / `buildBackground(command, { cwd })` 的入口，但调度器没有使用它。即使方言缓存已正确探测，指定工作目录的 Windows 命令仍可能被错误包装。
3. `handleSetCwd()` 调用 `resolveRemoteCwd(client, cwd, previousCwd)` 时没有传 `connection.getHostId()`，因此 `ssh_cd` 在该路径固定走 POSIX 兜底。MCP `ssh_exists` 和 `ssh_get_host_load` 虽然用 `sessionKey` 生成方言相关的内部命令，调用 `remoteExec()` 时却没把 `sessionKey` 传给执行 wrapper。

**建议改法**：

- 为每个连接保存一个有界、可共享的方言探测 Promise；方言相关的首条 exec、`ssh_cd`、文件工具和传输操作先等待结果。探测失败要返回可见的降级信息，不要在未知的 Windows shell 上静默套用 POSIX。
- 让 `execScheduledStream()` 与后台 runner 接收 `cwd` 并直接传给 `DialectSpec.buildExec()` / `buildBackground()` 的 options。去掉执行器自己拼的 POSIX `cd` 前缀；POSIX 路径仍由 POSIX dialect 构造。
- `handleSetCwd()` 把目标 `getHostId()` 传给 `resolveRemoteCwd()`；MCP 的 exists/host-load 所有 `remoteExec()` 调用把 `sessionKey` 同步传入。用一处 helper 管理“构造命令所用方言”和“执行 wrapper 所用方言”，防止两者分叉。
- 对方言缓存过期、连接重建、跳板链末端变化分别定义失效和重新探测规则，避免复用旧主机的结果。

**验收**：在延迟方言探测的假 SSH server 上，首条 PowerShell/CMD 命令不会使用 POSIX wrapper；Windows `ssh_cd`、显式 `cwd`、虚拟 `cwd`、后台命令、`ssh_exists`、`ssh_get_host_load` 均由同一种目标方言构造与执行。真实 Windows CI 需要覆盖含空格路径和连接后立即执行的场景；没有该环境时只能证明本地调用参数正确，不能宣称现场兼容完成。

- CI 构建后生成可核验的 build metadata：Git SHA、package version、build timestamp；`npm run build` 现在生成 `dist/build-info.js`，daemon ping/启动日志和 MCP server version 使用这份元数据。仍需补充安装后 CLI smoke 对版本字段的验收。
- 文档记录开发态 MCP 配置使用源码仓库 `dist`，发布态 CLI 如何安装及如何确认 `command -v ssh-exec` 实际落点。
- 恢复 GitHub 认证后，用普通 fast-forward push 推送本地分支；不要 force-push。推送后对比 `origin/main` 与 HEAD SHA，并确认目标 Actions 运行在新 SHA。

**验收**：`ssh_exec`/daemon 返回的版本 SHA 与实际构建提交一致（不能硬编码当前的 `4fc6544`）；shell 中 CLI 路径和版本可查；远端 HEAD 与本地期望一致；未授权用户不会误以为旧云端代码已更新。

### P2：按需打开交互 shell，区分 SSH 连接与 PTY 状态

**证据位置**：`src/connection.ts:76-85,188-235`、`src/gateway.ts:68-79`。当前 Gateway 普通会话已经传 `openShell:false`，直接使用 `SSHConnection` 的旧调用仍默认打开 shell；`openShell()` 现在有独立 timeout。shell channel 关闭时仍会触发连接的 disconnected 事件，transport 与 PTY 的事件模型还没有完全分离。

**剩余改法**：把“SSH transport ready”和“交互 shell 已打开”分开管理。普通 exec 与 SFTP 已能在 transport ready 后使用连接；只有 `--shell`、发送键盘输入或调整终端大小时才按需打开 shell/PTY。shell 单独关闭应报告 shell 事件；底层 hop 关闭才将 SSH transport 标为断开。会话复用、idle 清理与错误恢复需沿新的双状态模型检查。

**验收**：仅允许 exec/SFTP 而拒绝 PTY 的隔离 SSH server 上，命令和传输仍可建立连接；交互 shell 被拒时返回明确错误且不影响其他 channel；shell 打开回调不返回时能按时结束；多跳与现有交互模式无回归。

### P2：日志可诊断性与敏感数据治理

当前没有找到 debug log 文件，scheduler event JSONL 保存生命周期，task/output 保存命令与结果片段。权限目前为目录 `0700`、事件文件 `0600`，但命令可能带 token、路径或业务数据。

- 事件记录保留结构字段但对命令做 secret 参数脱敏；默认不在事件记录内存完整 stdout/stderr。
- debug log 显式创建 `0700` 目录和 `0600` 文件，并对 URI/token/password/private key 标记脱敏。
- 增加只读 `ssh-tool diagnostics` 输出：版本 SHA、daemon PID/启动时间、最近状态计数、保留期、文件数和错误码分布；不输出原始命令、host/user 或输出内容。
- 对终态 task、outputs、events 的保留期和清理数生成回执，清理行为不要在测试进程中作用于生产目录。

**验收**：放入带测试 token 的命令后，event/debug/diagnostic 三种产物均不包含明文；权限在 umask 0022 下仍满足；用户可看见每次清理的数量和截止时间。

## 建议实施顺序

1. **先修 test isolation**，避免后续测试继续清理或污染用户日志；从现在开始所有验证必须用临时 data/cache 根目录和 Unix socket 目录。
2. **关闭 shell 解析绕过**，新增重定向、`$()`、反引号与中性片段内嵌执行等分类用例；无法完整识别的组合设成需确认。
3. **修 Windows 方言调用链**，让首条命令等待有界探测，并统一 `ssh_cd`、前台/后台 cwd、exists 与 host-load 的构造和执行方言。
4. **完成传输原子性和默认 deadline**，为 CLI、MCP、daemon 与单文件/目录分支保持一致语义。
5. **同步扩展测试桩与 CI**，让 `test:ssh` 原 312 项和新增回归项全绿；在隔离目录里做 npm 打包完整性与装包 smoke，修复 `dist/remote-dialect/` 遗漏后才能发布 npm 包。
6. **建立本地/云端 SHA 可见性和发布检查**；待 GitHub 认证恢复后再普通 push。按需打开交互 shell 作为独立兼容性阶段。
7. **完成日志脱敏与 diagnostics**，保留期清理需有摘要，避免再出现无法判断是用户运行还是测试运行的日志。

## 不纳入本轮结论的事项

没有真实 Windows SSH 服务端和新版本部署后的用户执行日志，因此 Windows SFTP 原子替换及实际业务故障影响尚未现场验证。调度器日志能表明状态机发生了什么，但无法证明某个远端命令的完整 shell 语义或副作用；要验证这些边界必须使用隔离测试主机。

## 结论

**常用功能的风险高于远端协调器。**默认的 `ssh-exec --command` 和 MCP `ssh_exec` 都进入调度器。复审发现的复合命令风险、shell 语义改变、exec/SFTP deadline、异常退出码、下载临时文件替换和传输方言问题已在本次落地；剩余的扩展套件失败主要是旧测试桩与当前结构化契约不同步。

对旧审核文档做一次事实更新：它指出的“未校验 SSH 主机密钥”已不适用于当前代码。`src/known-hosts.ts:16` 默认使用 `accept-new`，`src/connection.ts:327-339` 为各跳设置 `hostVerifier`；显式配置 `strictHostKeyChecking: "no"` 仍可绕过校验，应仅由使用者有意识地选择。

协调器服务端**并未自动安装**，当前机器上也没有证据显示它被使用。现在 daemon 也默认关闭协调器调用；只有 `SSH_TOOL_ENABLE_COORDINATOR=1` 或显式构造选项才启用。它在本报告仍是条件性次要问题。

## 问题清单：先常用链路，后协调器

### P0（已修复）：复合命令可能绕过调度器的风险确认与互斥锁

原实现先命中第一个候选规则，导致 `echo ok; rm -rf <path>` 和 `pwd && systemctl restart example` 被当成只读。现在 `src/scheduler/command-classifier.ts` 会扫描全部顶层片段，取最高风险；未识别的复合片段也会保守要求确认。新增回归测试覆盖前缀、管道和未知片段；复现只调用分类函数，没有执行危险命令。

修复应先完整解析所有顶层命令段，取最严格的 `risky/mutates/cost`，不应首个匹配即返回；无法可靠解析的复合命令保守提升风险。增加 `;`、`&&`、`||`、管道、换行、shell 包装以及带只读前缀的危险命令表驱动测试。验收：上述两条复合命令均需要确认并取得正确锁。

### P1（已修复）：命令执行被拆成独立 shell，语义和超时均被改变

原实现会在 `src/daemon.ts` 和 `src/remote-shell.ts` 将分号片段拆成多个 `client.exec`。现在整条命令交给方言 wrapper 的单个远端 shell；timeout 只使用一份总 deadline。新增测试确认一条复合命令只打开一个 channel。

修复：默认整条命令只开一个 channel，由远端 shell 处理分号；分类器可分析分段，但执行器不改写用户语义。总超时从发起 `client.exec` 前开始，以单一 deadline 覆盖整条命令。验收：变量、`cd`、循环、错误码与分号链均符合原 shell，整条任务不超出 deadline 加可控清理时间。

### P1（已修复）：常用执行链路可无限等待，异常断开可误报成功

daemon runner 和兼容 facade 现在都在调用 `client.exec` 前启动 deadline；迟到的 channel 会被关闭。无退出码的 `close` 返回错误而不是成功；新增了无回调、无退出码和超时测试。

修复：把前置超时与异常关闭处理收敛到一个有界执行原语，daemon runner、兼容 facade 和内部 exec 共用。对无法确定远端是否仍在运行的情形返回明确的 `remoteProcessMayContinue` 或等价状态，避免自动重试造成重复副作用。验收：未调用 exec 回调、连接中断、无退出码 close、超时后迟到回调都只结算一次，且不会报成功。

### P1（部分已修复）：传输超时与覆盖安全不完整

SFTP 打开、传输和下载写入现在都受 deadline 约束；CLI/MCP 已暴露 timeout，下载先写唯一临时文件并在完成后替换目标。远端上传仍沿用现有 SFTP 目标写入路径，远端原子替换需要单独兼容不同服务器的 rename 语义，列为后续增强。

默认覆盖直接写目标：本地小文件下载用 `writeFileSync(targetLocalPath, ...)`，大文件下载用 `createWriteStream(targetLocalPath)`（`file-transfer.ts:1206,1235`）；远端上传亦直接打开目标写流。中途失败可能留下被截断的目标文件。`backup` 策略的远端移动命令只 `await remoteExec` 而不检查 `result.code`（`:365-369`）；本地备份失败也继续覆盖（`:569-580`）。建议用同目录临时文件写入、校验后原子替换；备份失败立即报错，不继续覆盖；超时从操作入口开始，覆盖探测、开 SFTP、读写和校验。验收：模拟中断时原目标保持完整，部分文件可识别并清理；无 SFTP 回调按时结束。

### P1（已修复）：Windows 传输的远端方言未从调用方传入

此前公开传输入口没有传 `sessionKey`，Windows 会回退到 POSIX。现在 daemon 和 MCP 在传输入口填入目标 host id，CLI 的 timeout 也会下传；真实 Windows SSH 端到端验收仍缺少日志证据。

修复：在连接建立后把目标的 `connection.getHostId()` 显式传入传输选项，并在 Windows CI 上用 CLI/MCP 公开入口验证文件和目录上传下载。对连接后立即调用方言功能的竞争，等待有界探测或使用 profile 中的显式 hint。

### P2：连接强制打开交互 shell，增加无关失败点

`src/connection.ts:76-79,188-222` 在 SSH 认证后强制 `client.shell()`，`openShell` 没有独立超时；shell 回调不返回时连接可长期停住。若服务端只允许 exec 或 SFTP、拒绝 PTY/shell，原本可用的命令和传输入口也无法建立会话。建议按需打开交互 shell：普通 exec/SFTP 只要求 SSH ready，`--shell` 或交互工具再开 PTY。保留明确的 shell 打开超时。此项是代码和架构风险，未在受限远端实测。

### P2：超时说明、daemon 等待与 IPC deadline 不一致

MCP `ssh_exec` 参数说明默认 30 秒（`src/mcp-server.ts:930`），`daemon.ts:1035` 对缺省调度任务实际等待 120 秒，`src/daemon-client.ts:231-232` 的 IPC 超时也固定 120 秒。daemon 恰在边界附近返回时，客户端可能先报 IPC 超时，而远端任务仍在执行；调用者若按失败重试，可能重复执行。建议区分命令执行 deadline、同步等待时长和 IPC 传输余量，在返回中稳定提供 `taskId` 与 `waitTimedOut`，并把文档值与行为对齐。此项由调用路径推得，尚未做边界时序实测。

### P2（条件性，协议已修复）：协调器 SSH helper 请求可能占用 channel

原实现把请求写成字面量 `\\n`，且没有关闭 stdin 或请求 timeout。现在使用真实换行、关闭 stdin、响应大小上限和 3 秒 deadline；新增了 helper 无响应和帧格式回归测试。协调器默认关闭，因此未启用时不会增加普通命令的 helper channel。

启用协调器时仍需在隔离主机验证 helper 部署和 channel 回收；现有本地记录不能证明远端 helper 已安装或发生过资源耗尽。

### P2（条件性，竞态已修复）：协调器租约生命周期存在可复现竞争

`task-scope.ts` 现在会在 late begin 返回后立即发送 `finishTask(cancelled)`，不启动 heartbeat；新增延迟 begin/提前 finish 回归测试。启用协调器后的远端租约仍应通过隔离环境检查。

### P3：协调器部署与用户可见结果没有闭环

`daemon.ts:878` 丢弃 `scope.begin()` 的 `CoordinationMetadata`；冲突和不可用 warning 没有进入 CLI/MCP 结果。`src/coordinator/installer.ts:35-43` 把带签名的字节保存为候选目录中的**单个文件**，而 systemd `ExecStart` 指向 `/opt/ssh-tool-coordinator/current/server-main.js`；目前没有产品路径调用安装器。`server-main.ts:8-12` 仅创建数据库目录，systemd unit 未声明 `RuntimeDirectory`，首次启动的 `/run/ssh-tool-coordinator` 没有创建保证。服务器 `server.ts:89` 把身份标为 `self-asserted`；这类冲突信息不应作为强制授权依据。

建议明确产品目标：若只需“冲突提醒”，在本地控制面实现可观测、可关闭的只读告警；若确实要远端协调，则补齐打包、上传、原子切换、运行目录、socket 权限、版本兼容、健康检查及回滚，并把 warning 放进 CLI/MCP 的结构化响应。`daemon.ts:862` 仍将 `sshUser` 写为 `unknown`，审计价值有限。首次部署必须在隔离主机验收，不应直接在现有远端机器上试装。

### P1：默认 CI 不覆盖新增模块且有错误的绿色信号

`package.json` 的 `test:fast` 是逐个列文件的硬编码清单，新增测试容易遗漏。17 个根级测试文件未被任何脚本点名；默认 `npm test` 现在 613/613 通过，但 `test:ssh` 仍有 8 项旧测试桩/契约失败。`.github/workflows/cross-platform.yml:68` 运行 `test:xplat`，但 `src/__tests__/xplat/lifecycle.test.ts:48-59` 在 sshd 不可达或认证失败时把整组测试 `skip`，仍可给出绿色作业。后续应自动发现离线测试，逐项同步扩展套件桩契约，并让真实 SSH 前置条件不足时失败、`skip=0`。

### P2：日志保密、留存和维护成本

调度事件原样记录命令，debug logger 的 `log()` 也直接序列化任意数据（`src/logger.ts:120-132`）；`enableDebug()` 将命令片段放入文件名，并用默认 umask 创建日志目录及文件（`:90-106`）。当前未发现实际 debug 文件，因此这里只是代码层风险。建议统一对凭据字段和常见 secret 参数做结构化脱敏；debug 文件使用 `0700` 目录/`0600` 文件、避免在文件名中放命令；导出诊断包时再次脱敏。保留期及容量上限应适用于遗留目录，并先做只读清单和备份确认，再迁移或清理。

`daemon.ts`、`mcp-server.ts`、`file-transfer.ts`、`scheduler-service.ts` 各超过千行，接口转换和任务状态分散。建议先统一 SSH exec 的总超时、异常关闭和结果语义，再统一传输 deadline/原子覆盖；用共享原语减少 CLI/MCP/daemon/兼容 facade 之间的行为漂移。稳定后再按“协议/编排/存储/适配器”拆模块，不为行数而拆分。
